## Question and bounded scope

Can two serving runtimes execute a declared amount of work, preserve a small task-quality contract, and produce auditable client latency and goodput measurements? Target use case: short interactive extraction from learner-authored service notes. This is a measurement pilot, not a production-capacity claim or runtime winner selection.

Candidate hardware/model: one H100 80GB HBM3, Qwen/Qwen2.5-32B-Instruct BF16 at revision `5ede1c97bbab6ce5cda5812749b4c0bdf79b18dd`, max context 4096, maximum active requests 4. Keep both runtimes on the same allocation if a reproducible dual-environment launcher is actually supported; otherwise mark comparisons unpaired and do not imply same-device evidence. Never mutate/recreate the provider Pod to switch runtimes without a newly bound lifecycle. Images, exact supported flags and CUDA compatibility are being checked against official sources.

Candidate runtimes: vLLM 0.29.0 and SGLang 0.5.20, each with prefix reuse disabled, BF16 weights/KV, no quantization, speculation, adapters or constrained decoding. Use explicit neutral generation defaults and repetition penalty 1. Proposed memory fractions are 0.90 with distinct runtime semantics; abort at 95% observed total device memory after load/graph capture. See [source-verified controls and immutable image references](runtime-preflight.md). These versions preserve continuity with Episode 0; availability/compatibility must be verified rather than assumed. HF/PyTorch control is deferred to keep tomorrow's pilot bounded. No optimization is in the core matrix. First later optimization is within-runtime prefix reuse on/off, after this baseline establishes exact-token accounting.

Predeclared hypotheses are deliberately modest: (1) both candidates can honor the same exact fixed-work and natural-stop contracts; (2) client timing and throughput reconcile with all scheduled attempts and a common cell interval; (3) each fresh block meets the small extraction quality gate. Runtime differences are descriptive pilot observations. Rejecting a hypothesis is a retained outcome, not a reason to tune the workload or discard a block.

Use three separately started, warmed and measured runtime blocks per runtime, paired order `A→B`, `B→A`, `A→B` with seed 20260923. Three pairs cannot perfectly balance first position; disclose it. Record block startup/exit evidence and fresh process identifiers privately. Repetition labels alone do not prove independent restarts. Same-device blocks remain conditional on one GPU allocation; they do not establish variation across GPUs/providers.

Core measured cells per block:

| Cell | Work | Requests | Concurrency | Deadline |
|---|---|---:|---:|---:|
| fixed-short | 512 exact rendered input tokens, exactly 128 output tokens | 32 | 1 | 180 s cell / 30 s request |
| fixed-medium | 2048 exact rendered input tokens, exactly 128 output tokens | 32 | 4 | 120 s cell / 30 s request |
| natural-quality | 24 authored labeled extraction tasks, max 128 output tokens, natural EOS | 24 | 1 | 120 s cell / 20 s request |

Total measured intent: 528 requests, 384 fixed-output requests and 144 natural-stop requests across six blocks. Natural tasks have 24 unique examples, not 144 independent quality examples. Four warmups for each cell per block (72 total) are separately identified and excluded. A cell timeout must cancel/drain all requests and retain every scheduled attempt. The two fixed cells are workload anchors; because both length and concurrency differ they cannot identify either factor's independent effect.

Freeze prompts, exact template and tokenizer provenance, rendered input token IDs and hashes, per-request ordering, gold labels, scoring implementation and corpus SHA-256 before live traffic. Generated deterministic filler must tokenize to exact target length or fail preflight; do not call an approximate 511-token prompt 512 tokens. Corpus can be public authored material; raw responses remain private. Fixed-mode requests set supported `ignore_eos=true`, no stop strings, `max_completion_tokens=128`; validate actual length and stop reason. Natural mode leaves EOS enabled; any truncation is a separate outcome and fails task qualification. Temperature 0, top_p 1, seed 20260923; top_k disabled via each runtime's validated dialect. Match effective sampling, not just similarly named flags. No adaptive prompt/cap/SLO changes after observing results.

Cold startup includes process creation through ready state and first valid request. Separate allocation/image/model download time. Each fresh runtime block performs all three warmup shapes, then measurement; prefix caching disabled and fresh process evidence provide no-reuse control. Kernel warmup is intentional. No cold and warm latency pooling. Alternate fixed-cell order by pair using one frozen schedule, matched within each pair; natural-quality always after both fixed cells. Record thermal/clock drift and cache state, and explain that this is still a small pilot.

## Measurement and quality contract

The public-comparability target is now the standard split documented in
[benchmark-standard.md](benchmark-standard.md): ShareGPT through one common
serving harness for latency/throughput, full `lm-eval` GSM8K for model-quality
parity, and the 24 authored extraction tasks only as a project-specific
application conformance gate. The existing fixture remains useful for local
harness validation, but it is not standard benchmark evidence and must not be
presented as such.

Client monotonic timestamps: scheduled arrival `a`, transport invocation `b`, actual first HTTP write `s`, first nonempty content event `f`, last content-bearing event `l`, validated terminal event `d`. `b` separates connection/preparation delay from dispatcher lag. In closed loop, `a` is the slot-release eligibility time, not a fictional open-loop arrival trace. Record clock domain and UTC/monotonic anchors. Do not subtract clocks on different hosts.

Derive scheduling lag `(b-a)`, connection/send preparation `(s-b)`, total send lag `(s-a)`, TTFT `(f-s)`, E2E `(d-s)`, user elapsed `(d-a)`, terminal overhead `(d-l)` and client content span `(l-f)`. TPOT is `(l-f)/(N-1)` only with exact N≥2 and valid content timestamps. Label it client average output-token span; multi-token chunks do not expose individual token timestamps. Preserve content-event count and interchunk gaps separately. Single chunk with N>1 has zero observed content span, not proof of zero decode latency; flag coalescing and exclude it from a token-cadence SLO. Use streamed usage plus pinned-tokenizer/token-ID evidence; retain and explain differences for EOS/special tokens. Stop on unexplained token disagreement. Never retokenize individual chunks and sum them as exact total tokens.

Predeclared candidate gates (not empirical performance claims): fixed short TTFT≤1000 ms, fixed medium TTFT≤2000 ms, both E2E≤10000 ms. Natural task TTFT≤1000 ms and E2E≤5000 ms, plus schema-valid, semantically correct, nontruncated output. TPOT≤80 ms is a secondary diagnostic, not core goodput predicate because chunk coalescing is not token timing. Natural block quality: 24/24 parse/schema valid, at least 23/24 exact semantic answers. Keep parser/schema and semantic scores separate. A failed arm remains a result; no winner claims from a tiny test set.

For each cell use wall interval from eligibility of its first request to completion/cancellation of the last scheduled request. Include failed-request time and drain; exclude preceding warmup and cold load. Report all scheduled, dispatched, transport-success, fixed-length-valid, quality-valid, SLO-qualified, failed, timeout, cancelled, unsent and censored counts. Request throughput = successful / same wall seconds; token throughput = exact successful output tokens / same wall seconds; request/token goodput = qualified count/tokens / same wall seconds. Semantic task goodput only applies to natural mode; fixed mode is length-and-latency-qualified goodput, not useful-answer goodput. Missing SLO/quality/token evidence yields unavailable with reason, not zero or pass. Zero qualifying requests with complete evidence legitimately yields zero.

Per-block summaries are primary; pooled distributions are secondary and labeled with request and block counts. Show p50/p95 as descriptive; omit p99 from headline charts (if exported, descriptive with n and no reliability claim). With three pairs show paired points/range, no bootstrap confidence interval from individual requests, no significance or capacity claims. Preserve failures and incomplete blocks. No automatic performance retries; one bounded startup retry may consume only approved reserve, with its failed attempt retained and no replacement chosen for a favorable result.
