# Inference Lab publication

Turn retained, verified evidence into a coherent learning episode and direct-copy publication artifacts. The public name is **Token by Token** with the tagline **Inference Lab**. Do not introduce ORION as public branding.

## Start from sources, not recollection

Read [references/workspace-map.md](references/workspace-map.md) to locate the active experiment, retained evidence, canonical capstones, roadmap, episode registry, template, and public-repository candidate. Rediscover repository visibility, remote state, and license status on each publishing task; never infer them from an earlier episode.

Read [references/publication-contract.md](references/publication-contract.md) before drafting, packaging, reviewing, or publishing. It defines the editorial order, evidence boundaries, diagrams, screenshots, GitHub structure, security gate, paid-resource boundary, and external-action boundary.

If the request concerns an experiment result, read its manifest and compiled plan in full before using its data. Treat examples and historical artifacts as evidence inputs, never as permission for a live run.

## Workflow

1. Inventory the requested episode's retained material. Classify every claim and visual as actual experiment, local rehearsal, prior trial, setup failure, or planned work. Resolve inconsistencies in favor of primary evidence and state unresolved gaps.
2. Draft the Substack article first. Open with the problem and the series vision, teach the inference concepts needed to understand the experiment, then present setup, results, cost, limitations, and the next controlled experiment. Step 0 is a warm-up and must not name a winner.
3. Derive the compact LinkedIn version from the article. Begin with the problem or motivation rather than “I tested”; retain the essential setup, measured results, evidence limits, and next experiments.
4. Produce direct-copy artifacts and the GitHub episode package. Update the registry-driven episode table of contents and existing roadmap rather than creating another future-work list. Future episodes append the registry and instantiate the reusable episode template.
5. Render or preview substantive documents and visuals. Check figures at their target widths, links, labels, units, captions, alt text, copied HTML/plain text, and dashboard screenshots.
6. After substantive drafts exist, request an independent reader review using `gpt-6-astra` with `ultra` reasoning when that combination is available. Give the reviewer the draft, source evidence, and this contract; apply supported feedback and record dispositions. Use `gpt-5.6-sol` with medium reasoning for other bounded child work unless the user requests a different model.
7. Run the publication and security gates in the contract. Report what is ready, what remains blocked, and the exact files produced.

The ordinary output of this skill is a reviewable local package. Do not create paid resources, run a new paid experiment for missing screenshots, publish a post, push a repository, change visibility, choose a license, or message anyone unless the user explicitly instructs that action. A request to prepare a report or publishing package is not blanket authorization for those actions.
